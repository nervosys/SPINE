SPINE Documentation

SPINE Documentation

SPINE is a headless semantic browser and agent web stack: a daemon that fetches pages and returns structured Unified Representations, a binary wire protocol (spine-wire v1) to talk to it, and a signed mesh and naming layer for agents to find each other.

What is SPINE?

SPINE provides an agentic web stack:

  • Headless semantic browsing — Navigate web pages and extract structured Unified Representations instead of raw HTML
  • Native wire — spine-wire v1: length-prefixed binary frames, deterministic CBOR bodies, a HELLO/HELLO_ACK handshake and a closed set of 19 commands (see Protocol)
  • Confidentiality — On the native client wire, confidentiality and authentication come from TLS (optionally mutual TLS) and nothing else. The mesh path between nodes is a different protocol with its own ML-KEM-768 and Ed25519 handshake (spine-session)
  • Naming and mesh — spine:// self-certifying names, signed name records, and an Ed25519-signed agent mesh
  • HLS scripting — Domain-specific language compiled to WebAssembly for server-side execution
  • Knowledge store — Per-session key/value entries with tags, through store_knowledge and query_knowledge
  • Research (not shipped) — Swarm intelligence, neural codecs, latent-space encoding, the memory subsystems and other experiments live in the separate research/ workspace and are not on the native wire

Quick Example

use spine_agent::AgentClient;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let mut client = AgentClient::connect("127.0.0.1:8080").await?;

    // Navigate and extract meaning
    client.navigate("https://example.com").await?;
    let ur = client.get_ur().await?;
    println!("Title: {}", ur.title);

    Ok(())
}

Quick Start

1. Start the Server

# Using the CLI
cargo run -p spine-cli -- deploy

# Or directly
cargo run -p spine-core

The server listens on 127.0.0.1:8080 by default.

2. Connect an Agent

Create a new project:

cargo run -p spine-cli -- init my-agent
cd my-agent

Or add SPINE to an existing project:

[dependencies]
spine-agent = { git = "https://github.com/nervosys/SPINE" }
tokio = { version = "1", features = ["full"] }
anyhow = "1.0"

3. Write Your First Agent

use spine_agent::AgentClient;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let mut client = AgentClient::connect("127.0.0.1:8080").await?;

    // Navigate to a page
    client.navigate("https://example.com").await?;

    // Get structured content
    let ur = client.get_ur().await?;
    println!("Page: {}", ur.title);
    println!("Elements: {}", ur.elements.len());

    // Execute HLS script
    let result = client.execute_hls("let x = 42 * 2; x").await?;
    println!("Computed: {:?}", result);

    // Measure latency
    let ms = client.ping().await?;
    println!("Latency: {}ms", ms);

    Ok(())
}

cargo run

Environment Variables

Common settings can be overridden with environment variables:

export SPINE_HOST=0.0.0.0
export SPINE_PORT=9000
export SPINE_TLS=true
export SPINE_TLS_MTLS=true
export SPINE_LOG_LEVEL=debug

Others include SPINE_METRICS_PORT, SPINE_MAX_SESSIONS, SPINE_TLS_CERT, SPINE_TLS_KEY, SPINE_TLS_CA, SPINE_HELLO_TIMEOUT, SPINE_IDLE_TIMEOUT, SPINE_SHUTDOWN_TIMEOUT and SPINE_CONFIG_PATH (an alternative config file path). See src/spine-core/src/config.rs for the full list.

Exposing the Daemon

The native server has no per-client authorization: any connected client can publish names and resources and call tools. A non-loopback server.host is refused at startup unless tls.mutual_tls is on or server.allow_unauthenticated_remote is set, which states that the network itself is trusted. TLS is the only source of confidentiality and authentication on the native wire.

Architecture Overview

SPINE is a headless semantic browser and agent web stack. The root Cargo workspace has 18 crates, each with a focused responsibility; experimental crates live in a separate research/ workspace (see Crate Map).

Design Principles

  1. Semantic-first — All content is parsed into Unified Representations, not raw HTML
  2. Agent-native — Built for programmatic access, not human browsing
  3. One wire — A single versioned binary protocol (spine-wire v1) with deterministic encoding, so every value has exactly one byte representation
  4. Honest security claims — Native-path confidentiality comes from TLS; the mesh has its own signed and encrypted handshake; research code is labelled as such
  5. Zero-copy where possible — Transport avoids unnecessary allocations

┌─────────────────────────────────────────────────────────────┐

└─────────────────────────────────────────────────────────────┘

Data Flow

  1. Agent connects via TCP, TLS, or WebSocket to the spine-core daemon and exchanges HELLO / HELLO_ACK
  2. Commands travel as REQUEST frames whose body is a BrowserCommand in deterministic CBOR, handled by spine_protocol::connection::Connection
  3. Daemon fetches web content under its outbound policy and parses it to a UnifiedRepresentation
  4. Reply is a RESPONSE frame with the same request id, whose body is {ok: result} or {err: {code, message}}, optionally zstd-compressed
  5. Agent receives structured data for processing

Protocol

Bodies

The body of a frame is one deterministic CBOR item (docs/spec/00-wire.md C.3). The frame header’s request id is the only correlation id; no body carries one.

A REQUEST body is a command from a closed set of 19. A command without fields is the text of its name ("get_ur"); a command with fields is a single-entry map {name: fields}. A name outside the set is unknown_command; a known name with a defect (an unknown field, a wrong type, a present null for an optional field, a non-deterministic encoding) is invalid_request.

get_binary_capabilitiesnone

A RESPONSE body is a single-entry map: {ok: result} on success or {err: {code, message[, details]}} on failure. The result’s shape depends on the command; read_resource answers a ResourceChunk whose hash and data are byte strings, capability_query answers a capability advertisement (agent_id, capabilities) and tool_call answers the tool’s content.

Every body struct rejects unknown fields. Optional fields are omitted when absent. Byte fields are CBOR byte strings, never arrays of integers. A serde_json::Value field stays a value and is encoded as CBOR, with integer and float widths as in C.5.

Frame Format

The native wire is spine-wire v1 (specified in docs/spec/00-wire.md). Every frame has a fixed 15-byte header, all integers big-endian:

┌────────────┬─────────┬──────────┬──────────┬────────────────┬──────┐
│ Length (4) │ Ver (1) │ Type (1) │ Flags(1) │ Request id (8) │ Body │
└────────────┴─────────┴──────────┴──────────┴────────────────┴──────┘
  • Length: bytes after this field, 11 + len(body), at most the negotiated maximum (16 MiB; 64 KiB before the handshake completes)
  • Ver: 1
  • Type: HELLO, HELLO_ACK, CLOSE, PING, PONG, REQUEST, RESPONSE, STREAM_* and EXT
  • Flags: bit 0 means the body is zstd compressed; other bits must be zero
  • Request id: correlates a RESPONSE with its REQUEST; a PING and its PONG share one
  • Body: exactly one deterministic CBOR item

A connection starts with HELLO from the client and HELLO_ACK from the server; nothing else may be sent first. The daemon closes a connection that has not sent HELLO within server.hello_timeout_secs (default 10 seconds) with CLOSE(timeout). A violation ends the connection with a CLOSE code (malformed_frame, frame_too_large, protocol_violation, …).

The current daemon runs one request per connection at a time (max_inflight = 1). A command travels as a REQUEST; the daemon’s reply travels as the RESPONSE with the same request id. Ping and Pong are the PING and PONG frames, whose body is an unsigned integer token.

Compression

Compression is off unless the sender turns it on. A body of at least 1 KiB is then compressed with zstd when that makes it smaller, and the compressed flag is set in the header. Smaller bodies are never compressed. The receiver needs no setting.

Security

See THREAT_MODEL.md for the full threat model.

Native Client Wire

The native wire between an agent and the spine-core daemon is spine-wire v1 (Protocol). It does no encryption of its own. Confidentiality and authentication on this path come from TLS only, with optional mutual TLS for client certificates. A plain TCP or WebSocket connection is plaintext.

There is no SPINE-level encryption, obfuscation, morphing, padding, pre-shared-key AES-GCM, post-quantum protection or traffic-analysis resistance on the native wire. The wire’s contribution to security is structural: bounded frames (64 KiB before HELLO, 16 MiB after), strictly deterministic CBOR bodies that reject malformed input, and closed command and error sets.

The daemon applies an outbound fetch policy to navigate (the outbound_* error codes), a per-IP connection limit, and a HELLO timeout.

Mesh Path

Node-to-node mesh traffic is a different protocol. spine-session performs a signed ephemeral ML-KEM-768 exchange with Ed25519 identity signatures and derives AES-256-GCM session keys, giving forward secrecy per connection. Mesh envelopes and name records are independently signed with Ed25519, so authorship can be checked without trusting the transport. The session handshake is custom cryptography that has not had external cryptographic review. Details and limits are in the spine-session crate documentation and THREAT_MODEL.md.

Research (not deployed)

The following exist only in the separate research/ workspace and are not in the native wire or the mesh handshake: the Chameleon latent-space key and latent AEAD (research/spine-protocol-research), the custom RLWE key exchange (research/spine-crypto), an X3DH example (research/spine-agentic), and stake-weighted Sybil resistance (research/spine-cluster). They are experimental and unreviewed. The earlier “security levels” table (Standard, Hardened, PostQuantum) described this research code, not a deployed feature.

Connecting

Transport Options

Every constructor runs the spine-wire v1 handshake (HELLO / HELLO_ACK) before it returns, with a ten-second deadline. TLS is the only thing that protects the connection; plain TCP and ws:// are plaintext.

TCP (plaintext)

#![allow(unused)]
fn main() {
let mut client = AgentClient::connect("127.0.0.1:8080").await?;
}

TLS

#![allow(unused)]
fn main() {
let mut client = AgentClient::connect_tls(
    "127.0.0.1:8080",
    "spine.example.com",
    Some(Path::new("certs/ca.crt")),
    None, // No client certificate
).await?;
}

Mutual TLS

#![allow(unused)]
fn main() {
let mut client = AgentClient::connect_tls(
    "127.0.0.1:8080",
    "spine.example.com",
    Some(Path::new("certs/ca.crt")),
    Some((Path::new("certs/client.crt"), Path::new("certs/client.key"))),
).await?;
}

WebSocket

#![allow(unused)]
fn main() {
let mut client = AgentClient::connect_ws("ws://127.0.0.1:8081").await?;
}

Auto-Reconnect

#![allow(unused)]
fn main() {
use std::time::Duration;

let mut client = AgentClient::connect_with_retry(
    "127.0.0.1:8080",
    5,                          // max retries
    Duration::from_secs(1),     // base delay (exponential backoff)
).await?;
}

connect_tls_with_retry(addr, domain, ca_path, client_cert, max_retries) does the same over TLS. AgentClient::over(stream) runs the handshake on a stream you already hold.

Connection Lifecycle

  1. Connect — Establish the TCP/TLS/WS connection and complete HELLO / HELLO_ACK
  2. Use — Send commands, receive responses; the daemon answers one request at a time (max_inflight = 1)
  3. Drop — Connection closes when AgentClient is dropped

The connection is stateful — the server maintains session state (the loaded page, cached UR, knowledge) per connection.

Errors

When the daemon answers {err: {code, message}} the returned anyhow::Error holds spine_protocol::native::NativeError::Remote { code, message, details }. Branch on the code, never on the message:

#![allow(unused)]
fn main() {
use spine_protocol::native::remote_code;

if let Err(err) = client.get_ur().await {
    match remote_code(&err) {
        Some("no_page_loaded") => { /* call navigate first */ }
        Some(code) => eprintln!("daemon refused: {code}"),
        None => eprintln!("connection problem: {err}"),
    }
}
}

call_tool is different: a tool failure comes back as Ok(ToolOutcome::Err { code, message, details }); only protocol-level failures are Err(..). The error codes are listed in Protocol.

Streaming

spine-stream provides reactive streaming with multiplexing and flow control.

It is a library with its own message types; it is not the native wire’s streaming. spine-wire v1 reserves frame types STREAM_START, STREAM_TOKEN, STREAM_END and STREAM_CANCEL (0x20 to 0x23), but no command streams yet: every one of the 19 commands is a single REQUEST and a single RESPONSE. Its LatentVector and LatentBatch stream items carry embeddings as data and are not an encryption or encoding layer.

Features

  • Reactive streams — Backpressure-aware data flow
  • Multiplexing — Multiple logical streams over one connection
  • Flow control — Window-based credit system
  • Priority queuing — Prioritized message delivery
  • Chunked transfer — Large payload streaming
  • Batching — BatchingStream with deadline-based partial emission

Tiered Caching

The spine-cache crate provides a three-level caching system optimized for agentic workloads.

Architecture

┌─────────────────────────────────────────────────┐
│                 TieredCache                      │
│                                                  │
│  GET:  L1 → miss → L2 → miss → L3 → miss → None│
│  PUT:  Write to all tiers (write-through)        │
│                                                  │
│  ┌──────┐    ┌──────────┐    ┌───────────┐      │
│  │  L1  │    │    L2    │    │    L3     │      │
│  │ LRU  │    │  mmap'd  │    │  Remote   │      │
│  │ RAM  │    │  files   │    │ delegate  │      │
│  └──────┘    └──────────┘    └───────────┘      │
└─────────────────────────────────────────────────┘

Cache Tiers

L1 — In-Memory LRU

  • Latency: ~10 ns
  • Capacity: Configurable max entries and byte size
  • TTL: Per-entry time-to-live
  • Eviction: Least-recently-used

L2 — File-Backed

  • Latency: ~1 μs
  • Storage: Memory-mapped files in configurable directory
  • Key Hashing: SHA-256 for filesystem-safe keys

L3 — Remote (Trait)

  • Latency: ~1 ms
  • Interface: RemoteCache trait for pluggable backends (Redis, Memcached, etc.)

Behavior

  • Read: Cascading miss from L1 → L2 → L3; on hit, promote to higher tier
  • Write: Write-through to all populated tiers
  • Invalidation: Per-key or namespace-wide clear

Ontology & Agent Discovery

SPINE includes a rich ontology system for agent self-description and mutual discovery.

Research. The ontology code is in research/spine-agentic, a separate workspace. The deployed discovery path is the spine-name crate and the find_providers and capability_query commands.

Overview

Every agent publishes an AgentOntology — a namespace-versioned vocabulary of capabilities, roles, and domain expertise. The ontology system enables:

  • Self-description: Agents declare what they can do, what data they handle, and what protocols they speak.

  • Url: Extract and normalize URL values.
  • List: Collect all matching elements into an array.
  • Record: Recursive sub-document extraction for nested structures.

Transforms

Transforms are applied in pipeline order after extraction:

  1. Trim — Strip leading/trailing whitespace
  2. Lowercase / Uppercase — Case normalization
  3. RegexCapture(pattern) — Extract first capture group

Example

let schema = ExtractionSchema::new("article")
    .field("title", "h1.title", FieldType::Text)
    .field("author", ".byline", FieldType::Text)
    .field_with_attr("link", "a.permalink", "href", FieldType::Url)
    .field_with_transform("date", ".pubdate", FieldType::Text,
        vec![FieldTransform::Trim]);

Protocol Negotiation

Every native connection (TCP, TLS, WebSocket, and QUIC when built) opens with one round trip of the spine-wire v1 handshake: the client sends HELLO and the server answers HELLO_ACK. Nothing else may be sent first. The specification is docs/spec/00-wire.md (sections C.5 to C.7 and C.10); the code is spine_protocol::hello (bodies and negotiate) and spine_protocol::connection::Connection (which sends and checks them). AgentClient::connect* and the daemon both go through it.

The earlier JSON VersionOffer / VersionResponse handshake and its ProtocolFeature list are gone. Nothing in the current code negotiates features by name; the only optional capability slot is extensions.

Bodies

Bodies are deterministic CBOR maps with text keys. HELLO and HELLO_ACK are open (unknown keys are ignored, so later versions can add fields); CLOSE is closed. Frames in the handshake are read under the 64 KiB pre-HELLO limit.

FrameKeys
HELLO (client, first)versions (strictly ascending, not empty), max_frame (1,024 to 16,777,216), extensions (no duplicates), agent (optional, at most 128 bytes)
HELLO_ACK (server)version, max_frame, max_inflight (at least 1), extensions, agent (optional)
CLOSEcode, message, supported (optional, for unsupported_version)

Rules

  • Version. The server selects the highest version offered that it supports. If there is none it sends CLOSE with unsupported_version and its supported list. Only version 1 exists.
  • Frame size. max_frame in the acknowledgement is the smaller of the client’s and the server’s limit, and applies to both directions from then on.
  • In-flight requests. max_inflight is the number of requests the client may have outstanding. The current daemon offers 1, so a client sends one REQUEST at a time; a second concurrent request is answered overloaded.
  • Extensions. extensions in the acknowledgement are the offered extensions the server supports, in the order the client offered them; the position is the extension index used by EXT frames. The current daemon supports none, and the SDK offers none.
  • Client check. The client rejects an acknowledgement that selects a version it did not offer, raises max_frame above its own, names an extension it did not offer, or carries max_inflight of 0, each as protocol_violation.
  • Timeout. The daemon closes a connection that has not sent HELLO within server.hello_timeout_secs (default 10) with CLOSE(timeout). The SDK waits ten seconds for HELLO_ACK.

The daemon’s offer is spine_protocol::native::local_config(): version 1, 16 MiB max_frame, max_inflight 1, no extensions. The SDK’s HELLO is native::client_hello(): version 1, 16 MiB max_frame, no extensions, and an agent string of the form spine-protocol/<version>.

Usage

use spine_protocol::hello::{negotiate, Hello, LocalConfig};

// Server side: frame is the first frame read from the peer.
let hello = Hello::from_frame(&frame)?;
let ack = negotiate(&hello, &LocalConfig::default())?;
let reply = ack.to_frame()?;
// Client side, after reading the acknowledgement:
// ack.validate_against(&hello)?;

An Err(Close) is the body to send in a CLOSE frame before closing. Most code does not call these directly: AgentClient::connect and Connection::client_handshake / Connection::server_handshake run the whole exchange.

Mesh Networking

SPINE agents can form peer-to-peer mesh networks for decentralized communication. The code is the spine-mesh crate; the handshake it runs is spine-session. This is a separate protocol from the native client wire (spine-wire v1, which has no mesh handshake and takes its confidentiality from TLS); the daemon reaches the mesh through the mesh_call and *_name commands.

Overview

The mesh networking layer provides:

  • Ed25519 signing identity: Cryptographic agent identity with fingerprinting
  • Peer-to-peer connections: Direct TCP, WebSocket and QUIC connections between agents, plaintext or with the encrypted spine-session handshake (ML-KEM-768 and Ed25519, AES-256-GCM frames; custom cryptography without external review)
  • Name records: Signed name records and their lookup RPC (spine-name, naming_mesh)
  • Multi-hop routing: Shortest-path message forwarding with TTL
  • Gossip protocol: Peer announcement propagation for network discovery
  • Message deduplication: Ring buffer preventing routing loops

Core Types

TypePurpose
Ed25519KeypairSigning keypair (ed25519-dalek)
SigningIdentityAgent identity with signing and verification
MeshNodeNetwork node with peer management and routing
MeshEnvelopeSigned message container with source, target, hops, TTL
MeshTargetDestination: Agent(id), Broadcast, Capability(name)
MeshPayloadMessage variants: agent messages, peer gossip, ping/pong, route request/response, knowledge sync, swarm invite/response, name records and resolution, and versioned application RPC

Routing

Messages are routed via shortest-path selection from the routing table. Routes are learned from incoming messages and gossip announcements. Stale routes are pruned periodically.

Agent A → MeshNode → [hop] → MeshNode → Agent B
              ↓                   ↑
          Route Table          Route Table

Gossip Discovery

Nodes periodically broadcast PeerAnnouncement messages containing their identity, capabilities, and known peers. Announcements propagate through the network with max-hop limits, allowing new nodes to discover the full topology.

Signature Verification

Every MeshEnvelope is signed by the sender using Ed25519. Recipients verify the signature against the sender’s public key from the trusted key store, rejecting messages from unknown or banned peers. The signature covers the id, sender, target, timestamp and payload; ttl and hops are rewritten by forwarders and are not signed, so treat them as advisory.
